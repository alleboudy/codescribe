# 10 — Bugzilla primer

If your bug tracker is Bugzilla, here's what you need to know to make sense of the RAG source-client code in [issue #5 §2](https://github.com/alleboudy/llm-finetuner/issues/5).

## What Bugzilla is

Bugzilla is a free, open-source bug tracker — one of the oldest still in active use (originally written at Netscape in 1998 for tracking Firefox/Mozilla bugs). It's a Perl webapp; modern installs run on Apache+MySQL/PostgreSQL.

Despite its age, Bugzilla is still widely deployed in:

- Open-source projects (Mozilla, Eclipse, GNOME, Red Hat).
- Enterprise IT shops with long-standing internal tooling.
- Telecom, defence, government.

If your org uses JIRA or GitHub Issues, you can skip this doc.

## The data model

### Bug

The top-level entity. Each bug has:

- **`id`** (integer; auto-incrementing).
- **`summary`** — the one-line title.
- **`description`** — the initial report body. Internally this is **comment 0**, the first comment in the bug's comment thread.
- **`product`** — top-level grouping (e.g., "Firefox").
- **`component`** — subdivision of a product (e.g., "Layout").
- **`version`** — affected product version.
- **`severity`** — `blocker | critical | major | normal | minor | trivial | enhancement`.
- **`priority`** — `P1 | P2 | P3 | P4 | P5` (org-defined; sometimes left empty).
- **`status`** — `UNCONFIRMED | CONFIRMED | IN_PROGRESS | RESOLVED | VERIFIED | CLOSED` (with intermediate states depending on Bugzilla version).
- **`resolution`** — set when status moves to RESOLVED/CLOSED; values: `FIXED | INVALID | DUPLICATE | WONTFIX | WORKSFORME | INCOMPLETE` (and a few more).
- **`assigned_to`** — the developer who owns fixing it.
- **`reporter`** — who filed it.
- **`cc`** — interested parties (notified on updates).
- **`creation_time`** — ISO timestamp.
- **`last_change_time`** — ISO timestamp; updates on any field change or new comment.

### Comments

Ordered thread on each bug. Comment 0 is the description; subsequent comments are replies/updates from anyone with permission.

Each comment has:

- `id`, `creator`, `creation_time`, `text`, `is_private` (some comments are restricted to project members).

### Attachments

Bugs can have attachments — patches, logs, screenshots, test files. Each has:

- `id`, `file_name`, `content_type`, `creation_time`, `creator`, `is_patch`, `is_obsolete`.

For RAG, attachments labelled `is_patch=true` are sometimes useful — they're often the literal fix diff. But the RAG plan in [issue #4](https://github.com/alleboudy/llm-finetuner/issues/4) focuses on linked Perforce CLs / Git PRs rather than Bugzilla attachments; attachments are scope-creep for v1.

### History

Every field change is recorded in a per-bug history log. You can query "when did this bug move from ASSIGNED to RESOLVED?" via the REST API.

## The REST API

Modern Bugzilla (4.4+) ships with a REST API. URL pattern: `https://<host>/rest/<resource>`.

### Auth

Two flavours:

- **Cookie-based** (after `POST /rest/login`): not friendly for scripts.
- **API key**: generated by the user in Preferences → API Keys. Sent as a header on every request:
  ```
  X-BUGZILLA-API-KEY: <key>
  ```

We use API keys exclusively. Store at `~/.config/<project>/bugzilla.key` (mode 600); load at startup; never log.

### Common endpoints

#### Get a single bug

```bash
GET /rest/bug/12345
```

Response (abridged):

```json
{
  "bugs": [{
    "id": 12345,
    "summary": "NullPointerException during application startup",
    "component": "core",
    "severity": "major",
    "status": "RESOLVED",
    "resolution": "FIXED",
    "creation_time": "2026-04-12T14:32:00Z",
    "last_change_time": "2026-04-15T09:11:00Z",
    "assigned_to": "jdoe@example.com",
    ...
  }]
}
```

#### Search bugs

```bash
GET /rest/bug?<query-params>
```

Query params:
- `last_change_time=2026-05-01T00:00:00Z` — bugs modified since.
- `product=Firefox` — filter by product.
- `status=RESOLVED&resolution=FIXED` — filter by status/resolution.
- `limit=100&offset=0` — pagination.
- `order=last_change_time ASC` — sort.
- `include_fields=id,summary,_default` — limit fields returned (smaller payload).

Pagination: max `limit` is server-configurable (default 100). Large `offset` values are slow; the RAG indexer prefers watermarking by `last_change_time`.

#### Get comments for a bug

```bash
GET /rest/bug/12345/comment
```

Response:

```json
{
  "bugs": {
    "12345": {
      "comments": [
        {"id": 1, "creator": "reporter@example.com", "text": "Steps to reproduce: ...",
         "creation_time": "2026-04-12T14:32:00Z", "count": 0},
        {"id": 2, "creator": "jdoe@example.com",    "text": "Reproduced. Looking.",
         "creation_time": "2026-04-13T08:01:00Z", "count": 1},
        {"id": 3, "creator": "jdoe@example.com",    "text": "Fixed in CL 67890",
         "creation_time": "2026-04-15T09:11:00Z", "count": 2}
      ]
    }
  }
}
```

Comment 0 (count=0) is the description.

#### Bug history

```bash
GET /rest/bug/12345/history
```

Returns the audit log of field changes. Useful for the temporal-pairing heuristic in [issue #4 §9](https://github.com/alleboudy/llm-finetuner/issues/4) — "when did the bug transition to FIXED?".

#### Attachments

```bash
GET /rest/bug/12345/attachment
```

Returns attachment metadata. The actual binary content is at `/rest/bug/attachment/<attach_id>` if you want it.

## Rate limiting

Bugzilla's API has no formal rate limit but **will get sluggish or refuse connections at >100 req/s**. The RAG indexer respects a token bucket capped at 5 rps by default ([issue #5 §3](https://github.com/alleboudy/llm-finetuner/issues/5)).

For initial bootstrap (~50K bugs, ~3 requests per bug for full detail with comments) at 5 rps that's ~30K seconds = ~8 hours. Tolerable for a one-time bootstrap. Subsequent incremental sync touches only deltas.

## Timestamps

Bugzilla emits timestamps as ISO 8601 with a `Z` suffix indicating UTC:

```
2026-04-15T09:11:00Z
```

Parse in Python:

```python
from datetime import datetime, timezone
ts = datetime.fromisoformat(s.rstrip("Z")).replace(tzinfo=timezone.utc)
```

**Subtle precision issue**: Bugzilla's `last_change_time` precision is **1 second**. If your watermark is `2026-05-20T12:34:56Z` and a bug changed at exactly that timestamp, you might miss it. Always subtract a 1-second safety margin when querying:

```python
watermark = last_seen - timedelta(seconds=1)
```

Documented in [issue #5 §2](https://github.com/alleboudy/llm-finetuner/issues/5).

## Authentication caveats

- **API keys are per-user.** If you query as a user without permission to see private bugs in a product, those bugs won't appear in your results (or you get a 403). For the RAG indexer, use a service account with broad read permissions.
- **Some bugs are private** (e.g., security issues during embargo). These won't appear in queries from non-authorised users. This is correct behaviour — don't try to bypass it.
- **API keys don't expire by default** but admins can revoke them. Test on bootstrap; if calls 401, regenerate.

## Versions in the wild

Bugzilla has been around for 25+ years. Versions you might encounter:

| Version | API |
|---|---|
| 3.x (very old; pre-2015) | XML-RPC only |
| 4.0–4.2 | XML-RPC + nascent REST |
| 4.4+ | Mature REST API |
| 5.x (current as of 2026) | REST is primary; XML-RPC still works |

We use REST. **Do not use XML-RPC** — it's deprecated, less performant, and harder to parse. [Issue #5 §2 AGENTS.md anti-patterns](https://github.com/alleboudy/llm-finetuner/issues/5) bans it.

## Comparison to other bug trackers

| | Bugzilla | JIRA | GitHub Issues |
|---|---|---|---|
| Self-hosted | yes | yes (Server/DC) | only via Enterprise |
| Open source | yes (Mozilla Public License) | no | no |
| REST API | mature | mature | mature |
| Cross-ref to git/perforce | manual (regex in comments) | bidirectional with Bitbucket; via Smart Commits to Git | bidirectional (closingIssuesReferences) |
| Granular permissions | strong | strong | weaker (repo-level) |
| Workflows / custom fields | limited | extensive | minimal |

For RAG purposes, the key differentiator is **how strongly the bug-to-fix link is enforced**:

- **GitHub** is best — `closingIssuesReferences` via GraphQL is gospel.
- **JIRA** is decent — Smart Commits / branch naming conventions give explicit links.
- **Bugzilla** is hardest — links are mostly free-text comments ("Fixed in CL 12345"); you need regex extraction + heuristics.

This is exactly why [issue #4 §9](https://github.com/alleboudy/llm-finetuner/issues/4)'s pairing module is more elaborate for Perforce+Bugzilla than the simpler git+GitHub equivalent.

## Common pitfalls

- **Bugzilla returns 400 with no body** on malformed JSON requests. Always send `Accept: application/json`.
- **Some Bugzilla configs default to HTML responses** for unauthenticated requests. Verify the `Content-Type` of every response.
- **`include_fields=_default`** is undocumented but works — it asks for the standard set of fields rather than every field. Speeds up queries.
- **`assigned_to`** is an email address in some installs, a username in others. Don't assume.
